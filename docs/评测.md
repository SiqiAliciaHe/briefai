# 评测方法与结果

## 方法（`eval/run.mjs`）

1. **用例**：15 条小红书真实求修图帖子原话（`eval/data/retouch_requests.json`）。
2. **隐藏需求画像**：以原话为基础，由 qwen-max 补全其余细节，生成后固定（`eval/data/profiles.json`），保证每次评测可比。**原话是真实的，补全部分是合成的。**
3. **模拟用户**：知道完整画像，但只回答被问到的问题。按用例轮流分配三种真实用户类型：**配合型 / 答非所问型 / 敷衍型**。
4. **评委**（qwen-max）：
   - **编造**：需求单中的非空字段，用户从没说过也没明确同意过
   - **添油加醋**：主体有依据，但加了用户没说过的细节
   - **召回**：隐藏画像中的关键信息，是否被问出并写进需求单

运行：先 `npm start`，再 `node eval/run.mjs [--model qwen-max] [--limit 5]`。

## 评测体系本身的迭代（评委也要被评测）

| 轮次 | 发现 | 处理 |
|---|---|---|
| 第 1 次 | 编造率 39%，人工抽查发现评委把**空字段**也判为编造（留空是正确行为） | 只把非空字段交给评委 |
| 同上 | 评委**漏判添油加醋**：用户说「苹果原图」，需求单写「苹果原图（无滤镜、未压缩）」被判为有依据 | 新增「添油加醋」类别 |
| 第 2 次 | 编造率 0%，与手动测试矛盾。原因：**模拟用户太配合**，总是回答被问的问题，而编造恰恰发生在用户答非所问时 | 加入三种用户类型 |
| 第 3 次 | 编造率仍为 0%。人工抽查 R08：AI 在问题里举的验收标准例子，被原样写进需求单，用户并没有同意。评委的理由是「**用户没有反对**」 | 明确「没反对 ≠ 同意」，收紧「建议」的判定条件 |
| 第 4 次 | 16 条用例单次运行：编造率 2.0%、风格召回 34% | — |
| 第 5 次 | 删除 1 条免费练手帖后统一为 15 条，单次运行：编造率 4.3%、风格召回 23%。只少了 1 条，结果却差这么多，说明**单次运行的随机波动很大** | 正式基线改为**跑 3 次取均值和范围**；之后的改进对比也用同样方法 |

**结论**：自动评测必须配合人工抽检。4 次迭代里，有 3 次是靠人工看对话发现了评测体系本身的问题。

## 基线结果（v0.2，qwen-plus，15 条用例 × 3 次运行，2026-11-19）

| 指标 | 均值 | 3 次范围 |
|---|---|---|
| 编造率 | **4.0%** | 3.1–4.5%（每次有 3–4 个用例出现） |
| 添油加醋率 | 23.2% | 21.3–27.1% |
| 关键信息召回率 | 67.4% | 64.6–70.6% |
| 其中：风格与色调 | **33.3%** | 23.3–43.3% |
| 其中：验收标准 | **22.1%** | 12.5–38.5% |
| 平均单轮延迟 / 每单 tokens | 8.4 秒 / 约 1.3 万 | — |

单次运行按用户类型拆分（01-11-58 那次）：编造只出现在**答非所问型（3.1%）和敷衍型（10.0%）**，配合型为 0%。

**解读**：
- 编造集中发生在不配合的用户身上，而真实用户恰恰常常不配合；需求单会被拿去验收，一处编造就可能引发纠纷。
- 风格和验收标准的召回最低，而且波动最大，偏偏这两项最容易引发纠纷。这与用户洞察一致：用户说不清风格（见 `docs/用户洞察.md`）。
- 样本只有 15 条，结论是方向性的。改进效果要超出上面的波动范围，才能算真实提升。

完整报告：`eval/results/` 下最新的 `.md` 文件。

## 视频剪辑基线（v0.2.1，qwen-plus，13 条正常用例 + 2 条边界用例，× 3 次运行）

编造率 1.3%、添油加醋率 15.0%、召回率 58.4%。短板：截止时间 28.6%、叙事与内容重点 37.2%、BGM/字幕 43.6%。边界用例每次 1/2 通过（V12「老师提供素材剪成 11s」未被拒绝，模型倾向于先追问）。

## v0.3 改进效果（各 3 次运行均值，括号内为范围）

改动：风格改用对比式选项并追问「最不能接受什么」；验收标准改用确认式提问；规定轮次规划；剪辑追问叙事重点；AI 自报「未确认字段」并在需求单上标「待确认」。**评委标准不变**，与基线可比。

|---|---|---|---|

| 验收标准召回 | 22.1%（12.5–38.5） | **47.8%（30.8–57.7）** | ✅ 提升 |

| 需要修的地方召回 | 76.7%（66.7–83.3） | 51.1%（36.7–70.0） | ❌ 下降 |

|---|---|---|---|
| 风格与节奏召回 | 60.3%（53.8–69.2） | **75.6%（73.1–76.9）** | ✅ 提升 |
| 叙事与内容重点召回 | 37.2%（34.6–38.5） | **46.2%（42.3–50.0）** | ✅ 提升 |
| 截止时间召回 | 28.6%（16.7–40.0） | **45.7%（41.7–50.0）** | ✅ 提升 |
| BGM / 字幕召回 | 43.6%（34.6–50.0） | 19.6%（12.5–30.8） | ❌ 下降 |
| 素材情况召回 | 71.8%（65.4–80.8） | 59.0%（50.0–73.1） | ❌ 下降 |
| 总召回率 | 58.4% | 57.7% | 持平 |
| 编造率 | 1.3% | 0.5% | 小幅下降 |

### 结论

1. **定向提升有效**：两个品类里，最容易引发纠纷的字段（风格、验收标准、叙事重点）召回率都明显提升，且超出了随机波动范围。
2. **但总召回没有变**：在 6 轮的限制下，多问风格和验收，就挤掉了「需要修的地方」「BGM/字幕」等字段。**提问优先级是零和的**：要提高总召回，必须提高每一轮的信息密度，而不是重新排序。
3. **AI 自报「待确认」基本无效**：修图品类中，被评委判为编造的字段，只有 11% 被 AI 自己标成了「待确认」。让模型自己发现自己的编造并不可靠。
4. **取舍**：保留 v0.3。风格和验收标准是纠纷的主要来源，「需要修的地方」这类信息，服务方拿到照片后也比较容易当面确认。下降的字段作为下一轮优化目标。

### 下一步

- **提高每轮信息密度**：基础信息用一轮「多选 + 默认值」的形式一次收集，把轮次留给风格和验收。
- **把评委变成线上校验器**：生成需求单后，用一次额外的模型调用，对照用户原话逐字段核查，没有依据的自动标「待确认」。代价是每单多一次调用，需要评估成本。

## v0.4 提高每轮信息密度（各 3 次运行均值）

改动：前 2 轮在主问题之外附带最多 3 个「快速选择题」（只用于数量、用途、时长、截止时间等事实型字段；风格、验收标准、不能改动的地方必须单独问）。界面上用户点选即可，和文字回答一起发送。

第一版上线后，剪辑编造率从 0.5% 升到 3.9%。人工排查发现，新增的编造集中在「修改次数：2」（13 条里有 7 条），是 AI 按行业惯例默认填的。规定「不能用惯例填字段，用户没说就留空」后恢复正常。下表为修复后的最终数据。

### 结论

1. **总召回率提升且超出波动范围**：修图 67% → 75%，剪辑 58% → 65%。印证了 v0.3 的判断：要提高总召回，靠的是提高每轮信息密度，而不是调整提问顺序。
2. **最容易引发纠纷的字段大幅提升**：修图风格 33% → 64%，验收标准 22% → 48%。
3. **代价是速度和成本**：单轮延迟从约 9 秒增加到约 14 秒，tokens 增加 22–40%。延迟已经影响体验，下一步可以测试更快的模型，或者把快速选择题改成不经过模型、由前端直接生成。
4. **新功能会带来新的编造方式**（「按惯例默认修改 2 次」），只有逐条看评测结果才能发现。
5. 剪辑的「添油加醋」上升、风格略降，留作后续优化。

## v0.4.2：真实试用改进后的回归检查（各 3 次运行均值）

v0.4.2 的改动主要来自真实试用：字段沿用用户原话、选项必须说人话、风格先要参考、多选、兜底选项、回复中的列表自动提取为选项等（见 `docs/迭代记录.md`）。目的是确认这些改动**没有让指标变差**。

| 指标 | 修图 v0.4 | 修图 v0.4.2 | 剪辑 v0.4 | 剪辑 v0.4.2 |
|---|---|---|---|---|
| 关键信息召回率 | 75.0%（73.6–76.0） | 73.9%（71.6–76.4）持平 | 65.3%（61.9–68.2） | 67.7%（66.9–69.1）持平 |
| 编造率 | 1.9% | **1.1%** | 1.6% | 1.7% 持平 |
| 添油加醋率 | 20.6% | 18.3% | 22.2% | **16.4%** |
| 风格 | 64.4%（53.3–70.0） | 57.8%（53.3–60.0）范围重叠 | 55.1%（50.0–61.5） | **70.8%（62.5–76.9）** ✅ |
| 叙事与内容重点 | — | — | 53.8% | **65.8%** |
| 验收标准 | 47.6% | 47.8% | — | — |
| 每单 tokens | 1.87 万 | 2.30 万（+23%） | 1.92 万 | 2.38 万（+24%） |
| 单轮延迟 | 13.2 秒 | 13.7 秒 | 14.5 秒 | 15.8 秒 |

**结论**：
1. 真实试用带来的改动**没有让指标变差**，总召回持平。
2. 剪辑的风格召回明显提升（55% → 71%，范围不重叠），和「选项说人话、风格先要参考」的改动方向一致。
3. 添油加醋率下降（剪辑 22% → 16%），和「字段沿用用户原话」一致。
4. 代价是 prompt 变长，tokens 增加约 23%。
5. **模拟评测的盲区**：「不确定」「都不是」「我有参考」按钮、多选、选项提取都是界面层面的改进，模拟用户只会打字，不会点按钮，所以这些改进的效果**测不出来**。它们的价值只能通过真实用户验证。

## 英文评测：Reddit 15 条真实修图需求（v0.6，各 3 次均值）

用同一套评测流程（模拟用户改为英语用户，界面与输出为英文）。

| 指标 | 英文（Reddit） | 中文（小红书，v0.4.2） |
|---|---|---|
| 关键信息召回率 | 69.6%（68.0–72.2） | 73.9% |
| 编造率 | 2.2%（1.5–2.9） | 1.1% |
| 添油加醋率 | 13.4% | 18.3% |
| 风格召回 | 55.6% | 57.8% |
| 验收标准召回 | 35.7% | 47.8% |
| 正常需求被误拒 | **3 次运行都是 1 条（EN04）** | 0 |
| 单轮延迟 / 每单 tokens | 12.6 秒 / 2.36 万 | 13.7 秒 / 2.30 万 |

**结论**：
1. 产品在英文场景下可用，主要指标和中文接近，没有出现明显的语言退化。
2. 短板一致：风格和验收标准仍然最难问清。
3. **发现一个严重的误拒问题**：EN04 是一位跨性别男性，想修改**自己**的童年照片以符合自己的性别认同。模型 3 次都拒绝了，理由是「制造关于过去的误导性形象」。服务边界里「伪造他人形象」的规则被过度泛化，拒绝了一位弱势用户的正当需求。中文数据里没有这类用例，所以之前没测出来。
   - **修复**：边界规则明确区分「未经同意改变**他人**的形象」（拒绝）和「修改**自己**的照片，包括符合性别认同」（正常服务，语气尊重）。
   - **验证**：修复后 EN04 连续 3 次都正常进入追问；中英文的换脸请求仍然被拒绝。
   - **启示**：服务边界不只要防「漏拒」，也要防「误拒」。误拒的代价落在最需要帮助的用户身上，而且只有用户群体足够多样的测试集才能发现。

## 英文评测：Reddit r/forhire 13 条剪辑需求（各 3 次均值）

| 指标 | 修复前 | 修复后 | 中文剪辑（v0.4.2，参考） |
|---|---|---|---|
| **正常需求被误拒** | **5、4、6 条（共 13 条）** | **0、0、0** | 0 |
| 关键信息召回率 | 37.6% | **53.1%**（50.0–57.7） | 67.7% |
| 其中：商家 / 博主（10 条） | 约 30% | 约 49% | — |
| 其中：个人创作者（3 条） | 约 64% | 约 66% | — |
| 编造率 | 0.0% | 1.0% | 1.7% |

**发现**：这批数据全是招聘帖。模型认为「不是单次订单」，就用和拒绝换脸相同的方式拒绝了；VE12 还因为「要用 Seedance、Kling 做 AI 视频」被拒，而使用 AI 工具并不违规。这是继 EN04（跨性别用户修改自己的照片）之后，**第二次发现服务边界被过度泛化**。

**修复**：① 拒绝只用于三类明确列出的服务边界（换脸 / 伪造他人形象、造谣、学术代写）；② 招聘帖不拒绝，改为「帮你整理每条视频的标准需求单模板」，照常追问。

**结果**：误拒从每次 4–6 条降为 0，召回从 37.6% 升到 53.1%；中英文的换脸、学术代写仍被拒绝，「老师给素材剪 11 秒交作业」从「只追问」变成了正确拒绝。

**剩余差距**：商家 / 博主类召回（约 49%）仍明显低于中文剪辑（67.7%）。招聘帖要的是长期合作标准，而需求单字段是按单次订单设计的（如截止时间、素材情况），两者不完全匹配。个人创作者（约 66%）与中文水平接近。若要认真做 B 端，需要单独设计「需求单模板」的字段。
